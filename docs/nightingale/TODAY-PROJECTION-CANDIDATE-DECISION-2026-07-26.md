## 2. Decision outcome

The first patient-journey contract candidate after encounter discovery is a Nightingale-owned
Today projection. It answers only:

> What released information is available to help this authenticated inpatient understand
> today?

It does not answer what clinicians privately believe, what the EHR contains, what the final
care plan will be, whether a test or discharge will happen at a particular time, or whether
the absence of a released item means that no care is planned.

The candidate establishes six core rules:

1. **Every patient-visible value carries its own governance context.** Release, freshness,
   uncertainty, language, correction, and offline behavior cannot be represented only once
   at document level.
2. **Empty and unavailable are different states.** A released-empty list means only that no
   items were released for that section after a complete governed evaluation. It never means
   that no care is planned. A not-available section contains no content and directs the
   patient to the care team.
3. **Only Nightingale-owned opaque handles cross the boundary.** The request uses the held
   encounter handle, and schedule items use new opaque item handles. No encounter, grant,
   principal, patient, staff, FHIR, EHR, or source-system identifier is exposed.
4. **Corrections replace; retractions withhold.** An effective released replacement may show
   a source-free correction notice. The response never exposes the withdrawn value, actor,
   reason, target identifier, or internal correction record.
5. **The server remains authoritative at disclosure time.** Identity, context, operation,
   release, field governance, race recheck, and durable audit gates are evaluated before one
   atomic no-store response.
6. **This is a design candidate, not implementation approval.** The executable Nightingale
   foundation still contains zero paths and every activation field remains false.

## 3. Why a new contract is required

The legacy Hummingbird Patient Today surface demonstrates useful patient-experience ideas,
but its contract cannot be renamed or copied into Nightingale.

### 3.1 Aggregate projection context can mislabel individual fields

The legacy response places one `uncertainty`, one `provenance`, and one aggregate freshness
record around a composite document. Today may combine:

- a schedule item from one source observation;
- a location label from another;
- discharge outlook produced and reviewed at a different time;
- translated prose released under a separate workflow; and
- a corrected field whose predecessor was withdrawn.

One document-level freshness or provenance statement can therefore make a field appear newer,
more certain, more directly sourced, or more recently reviewed than it is. Nightingale
requires a complete context beside every displayed value.

### 3.2 Legacy identifiers are product and authorization internals

The legacy projection returns `projection_uuid` and `encounter_uuid`; its broader patient
surface also uses grant UUIDs and raw authorization scopes. Those values are unnecessary for
rendering Today and create correlation, caching, compatibility, and inference obligations.

The candidate accepts only a Nightingale encounter handle already issued by the separately
held encounter-access operation and returns only a Nightingale content revision plus opaque
schedule-item handles.

### 3.3 Native clients currently represent different subsets

The legacy iOS model decodes care location and discharge outlook. The Android model decodes
headline, summary, schedule, next steps, and notices but omits those two Today structures.
Both clients turn a composite response into presentation models with different loss and
default behavior.

The candidate does not claim native parity. It instead creates a canonical fixture boundary
that future generated models must decode identically before networking can be enabled.

### 3.4 First-record selection is not an encounter rule

Both legacy native clients select the first encounter returned by the legacy list endpoint.
Nightingale has already rejected that behavior. Today is addressed through the one opaque
context handle produced by the separately held zero-or-one self-inpatient candidate. A
client-supplied source encounter identifier and a server-selected “first record” are both
prohibited.

### 3.5 A general content allowlist is not field approval

The legacy content guard has valuable defensive patterns:

- explicit top-level keys;
- recursive forbidden identifiers;
- bounded patient-language value shapes;
- release, uncertainty, provenance, and relationship checks; and
- patient-state vocabulary validation.

Those patterns are evidence, not clinical approval. A field still needs an authoritative
source, release authority, freshness policy, uncertainty wording, correction/retraction
behavior, language approval, and offline rule. Nightingale makes those decisions explicit at
the field boundary.

### 3.6 “No released items” must not be mistaken for “nothing planned”

The iOS and Android reference screens both use safe prose when Today is absent, but the
underlying list structure does not itself distinguish:

- no planned care;
- no released care;
- incomplete source evaluation;
- unavailable source;
- a withheld sensitive field;
- a retracted release; or
- a client decode failure.

The candidate uses section states and response errors to prevent those conditions from
collapsing into a misleading empty list.

## 5. Operation boundary

The held relative path is:

```text
GET /inpatient-contexts/{encounter_handle}/today
operationId: getNightingaleTodayProjection
```

It would sit under the already reserved `/api/nightingale/v1` namespace only after approval.
The path parameter must match `^ntg_enc_[a-z2-7]{50}$`.

The request deliberately has:

- no query parameters;
- no body;
- no client-supplied locale override in this initial candidate;
- no source identifier;
- no legacy identifier;
- no patient, principal, grant, or projection identifier;
- no authorization scope supplied by the client; and
- no permission for durable handle storage on the client.

The response locale comes from a future approved account/session preference decision. That
decision remains held; the fixtures use synthetic `en-US` only.

## 6. Authorization and disclosure sequence

An eventual implementation must evaluate all gates in this order or a demonstrably
equivalent fail-closed order:

```text
active contract operation
  -> product / operation / facility / cohort gates
    -> Nightingale realm, principal, session, and assurance
      -> verified, unmerged, self identity link
        -> opaque context handle owned by that principal
          -> authoritative current inpatient confirmation
            -> server-side Today capability
              -> effective release policy
                -> effective patient-language release
                  -> every displayed field's governance context
                    -> identity, context, capability, and release race recheck
                      -> durable request evaluation audit
                        -> durable field-disclosure audit
                          -> one atomic no-store response
```

No client-side cached capability, section presence, hidden control, legacy scope, encounter
ordering, or response from another product is authority.

The candidate is self-only. Representative access and sensitive-encounter behavior remain
held because their proof, consent, expiration, restriction, and disclosure rules are not
approved.

## 7. Response envelope

A successful response contains:

- `data.kind = "today"`;
- one opaque `content_revision` matching
  `^ntg_tdyrev_[a-z2-7]{50}$`;
- exactly eight named section objects;
- an optional source-free `revision_notice`;
- request, generation, policy, authorization-evaluation, inpatient-context-evaluation,
  locale, and completeness metadata; and
- an empty `links` object in this candidate.

It does not contain document-level provenance, freshness, or uncertainty. It does not expose
an encounter handle again, because the request already supplies the context. It does not
return an internal projection identifier.

Every template requires:

```text
Cache-Control: private, no-store, max-age=0
Pragma: no-cache
X-Robots-Tag: noindex, nofollow, noarchive
Vary: Authorization, Accept-Language
Content-Type: application/json
```

The candidate permits no durable client cache and declares every governed field online-only.
Offline retention, screenshots, operating-system backups, notification payloads, and
background refresh remain separately governed work.

## 8. Field-level governance

Every displayed value has exactly two members:

```json
{
    "value": "patient-visible value",
    "context": {
        "release": {},
        "freshness": {},
        "uncertainty": {},
        "language": {},
        "correction": {},
        "offline": {}
    }
}
```

### 8.1 Release

Each field records:

- `state = released`;
- an ISO-8601 `released_at`;
- the Nightingale patient-language content-policy version.

A document cannot make an unreleased field displayable by being released as a whole.
Clinical approval and patient-language approval are separate prerequisites even when one
workflow eventually captures both.

### 8.2 Freshness

The candidate permits:

- `current`; or
- `approved-stale`.

Approved-stale display requires a patient notice at that field. `unknown` is an uncertainty
level, not a permitted freshness shortcut. Mandatory content with unknown freshness fails
closed. A future freshness threshold must be approved per source/field class; this candidate
does not invent one.

### 8.3 Uncertainty

Each field has:

- `low`, `medium`, `high`, or `unknown`;
- a patient-language explanation; and
- a boolean stating whether it can change.

This context belongs to the field. A confirmed room and an estimated time window must not
inherit the same certainty.

### 8.4 Language

Each field has:

- a BCP 47-style locale matching the response locale;
- `approved-source-language` or `approved-translation`; and
- `plain_language_review = approved`.

Machine translation, silent locale fallback, untranslated staff prose, and a language label
without content approval are not accepted.

### 8.5 Correction

Each field is `original` or `corrected`. A corrected field requires a patient notice. The
optional root revision notice can tell the patient that part of Today changed, but it cannot
expose:

- the prior value;
- the correction actor;
- an internal reason code;
- the target/replacement record;
- an internal timestamp beyond the released field context; or
- staff review metadata.

### 8.6 Offline

Every field is `online-only`, with `durable_storage_permitted = false`. This is intentionally
stricter than a future offline design. A later proposal must separately address:

- session memory;
- protected local storage;
- expiration and revocation;
- device transfer and backup;
- screenshots and screen recording;
- push payloads;
- background refresh;
- correction/retraction propagation; and
- safe behavior after discharge or remote logout.

## 9. Section semantics

The candidate names eight sections:

1. `headline`;
2. `summary`;
3. `schedule`;
4. `next_steps`;
5. `care_location`;
6. `discharge_outlook`;
7. `questions`; and
8. `notices`.

Headline and summary must be released and governed for every 200 response. The six other
sections support explicit availability.

### 9.1 Released

The section contains governed values. This does not imply that it contains all operational
or clinical information—only the complete set authorized for that released patient section.

### 9.2 Released-empty

List sections may be released-empty only when the governed evaluation completed and produced
zero released items. The response must include a notice that this does not mean no care is
planned.

Released-empty with any item is a contract violation.

### 9.3 Not-available

The section contains no content and provides a patient-language care-team fallback. It does
not identify whether the reason is source, release, policy, sensitivity, freshness, or
translation.

Not-available with hidden or partial content is a contract violation.

## 10. Schedule items

A schedule item uses an opaque handle matching
`^ntg_tdyitem_[a-z2-7]{50}$`. Handles must be unique within the response and carry no source
meaning.

Every item field is separately governed:

- label;
- detail;
- status;
- time window;
- timing confidence;
- preparation;
- whether it can change.

The held status candidates are:

- requested;
- planned;
- confirmed;
- in progress;
- completed;
- delayed; and
- canceled.

The candidate artifact uses machine values with hyphenated `in-progress`. This is not a
clinically approved vocabulary release. Labels and cross-platform unknown-value behavior
remain subject to the patient-state vocabulary approval gate.

Timing confidence is:

- confirmed;
- estimated; or
- unknown.

An exact time or ETA claim is prohibited in this candidate. Patient-facing time windows must
be reviewed language and carry their own freshness and uncertainty context.

## 11. Care location

Care location can contain governed facility, unit, and room display names plus a governed
status:

- current;
- updating; or
- unknown.

It cannot contain a source location identifier, bed-management priority, capacity state,
staffing state, worker location, isolation detail, or a future destination that is not
released for the patient.

`updating` and `unknown` are first-class patient states. The client must not keep a prior
room label visible under a newer aggregate “current” badge when the field itself is stale or
withdrawn.

## 12. Discharge outlook

Discharge outlook can contain:

- a governed estimated range;
- governed timing confidence;
- governed readiness-topic values;
- governed remaining-step values; and
- governed `can_change`.

It is never:

- a discharge order;
- a promised date;
- a prognosis;
- an automatic inference from length of stay;
- a staff capacity or placement priority;
- a claim that every unresolved need is shown; or
- a substitute for speaking with the care team.

Unknown timing is a valid released patient state when approved wording explains it.

## 13. Release, correction, and retraction

The candidate requires one effective policy and one coherent effective release.

| Source state                                      | Patient result                                              |
| ------------------------------------------------- | ----------------------------------------------------------- |
| No released projection                            | Generic `404 not_found`                                     |
| Draft only                                        | Generic `404 not_found`                                     |
| Future release                                    | Generic `404 not_found`                                     |
| Effective retraction                              | Generic `404 not_found`                                     |
| Correction without effective released replacement | Generic `404 not_found`                                     |
| Effective corrected replacement                   | `200` with only replacement values and a source-free notice |
| Conflicting effective releases                    | Generic `503 temporarily_unavailable`                       |
| Policy-version mismatch                           | Generic `503 temporarily_unavailable`                       |

A correction never causes the withdrawn value to reappear from cache. A retraction never
falls back to an older release without a new independent release decision.

## 14. Error and non-disclosure behavior

The candidate defines:

| Code                            | Status | Intended use                                                                                                                         |
| ------------------------------- | -----: | ------------------------------------------------------------------------------------------------------------------------------------ |
| `authentication_required`       |    401 | Approved Nightingale authentication is missing, expired, or revoked                                                                  |
| `access_unavailable`            |    403 | The account, relationship, cohort, identity link, or sensitive-service state cannot use this experience                              |
| `not_found`                     |    404 | Product/operation/facility disabled; unknown or wrong-principal handle; closed context; capability denied; unavailable release state |
| `account_state_requires_review` |    409 | Opaque-handle mapping is internally inconsistent                                                                                     |
| `rate_limited`                  |    429 | Approved principal-specific request limit exceeded                                                                                   |
| `temporarily_unavailable`       |    503 | Source, database, content-integrity, field-governance, language, freshness, audit, or serialization safety failure                   |

Unknown, wrong-principal, malformed, closed, and authorization-race handles share the same
generic no-content surface. Responses never echo a handle or disclose whether an encounter,
release, correction, field, or source record exists.

The candidate intentionally avoids `500` as a patient contract. Internal failures map to a
bounded, patient-safe unavailable response after best-effort safety audit.

## 15. Audit requirements

Every 200 response requires:

1. one durable request evaluation event; and
2. one durable field-disclosure event that can prove which governed release set was
   disclosed without storing patient-visible values.

The audit contract prohibits:

- raw patient-visible values;
- raw context or item handles;
- source identifiers;
- staff actor identifiers;
- free text; and
- credentials.

Success fails closed if either durable audit cannot be recorded. Denial and safety-failure
audits are best effort so the audit sink does not become a new existence or availability
oracle.

The exact correlation, retention, access, legal-hold, incident, and patient-request semantics
remain approval work.
